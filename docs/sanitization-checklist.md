# Чек-ліст санітизації даних для роботи з AI

Робочий документ команди. Проходити **перед** тим, як документ клієнта
потрапить у будь-яку модель — включно з тією, що вбудована в IDE, і включно з
агентом, який «просто підсумує».

**Хто проходить:** той, хто збирається вставити документ у модель. Не
«відповідальний за безпеку» — той, чиї руки на клавіатурі.

**Коли спрацьовує:** новий бриф від клієнта · вигрузка з продакшену ·
лог або скріншот з інциденту · експорт воркфлоу n8n · будь-що з пошти чи
месенджера, що йде далі в модель.

---

## 1. Світлофор: що шукаємо

| Категорія | Приклади з наших проєктів | Куди можна |
|---|---|---|
| 🔴 Секрети | API-ключі, bot-токени, PAT, connection strings, вміст n8n credentials, приватні ключі | нікуди; лише через env на рантаймі |
| 🔴 PII клієнта і його замовників | ПІБ, email, телефон, адреса, нік у месенджері, ІПН/ЄДРПОУ | нікуди в публічну модель |
| 🔴 Продакшн-дані | вигрузки таблиць, логи із замовленнями, скріншоти CRM, дампи БД | нікуди; замінити синтетикою |
| 🟡 Внутрішня комерція | маржа, собівартість години, умови угоди, хто конкурент | лише enterprise / no-train |
| 🟡 Внутрішня логіка | схеми БД, назви внутрішніх сервісів, топологія, імена гілок | лише enterprise / no-train |
| 🟢 Постановка задачі | опис проблеми, критерії приймання, обсяги без даних | будь-яка модель |

**Правило вибору інструмента:** документ належить до **найвищої** категорії, що
в ньому лишилась. Один рядок 🔴 робить 🔴 увесь документ.

## 2. Чотири методи маскування

| Метод | Що робить | Приклад |
|---|---|---|
| **redaction** | прибрати повністю | `<REMOVED>`, `<INTERNAL>` |
| **masking** | лишити форму, прибрати значення | `+380 (XX) XXX-XX-XX`, `****-1234` |
| **synthetic** | замінити правдоподібним вигаданим | `[CLIENT_1]`, `orders@example.test` |
| **out-of-band** | значення не потрапляє в текст узагалі | `<SECRET_OUT_OF_BAND>` + ім'я env-змінної |

**Правило балансу.** Після маскування задача має лишатись зрозумілою. Якщо
модель більше не розуміє, що робити, — замасковано зайве. Якщо поле збережене
«щоб було» — замасковано замало.

Практичний тест: перечитайте санітизовану версію і спитайте себе, чи змогли б
ви за нею написати технічну специфікацію. Якщо ні — ви щось перерізали.

> **Не відтворюйте форму секрету.** `xoxb-<TOKEN>`, `sk-live-<KEY>`,
> `postgres://user:<PASS>@host/db` — усе це витік структури, навіть коли
> значення вигадане. Сканери секретів реагують на префікс, а людина по формі
> впізнає сервіс. Пишіть `<SECRET_OUT_OF_BAND>` і окремо — ім'я env-змінної.

## 3. Перед тим, як вставити в модель

### 3.1 Пошук по характерних рядках

> **Запускайте це у власному терміналі, а не в AI-сесії, і рахуйте збіги, а
> не друкуйте їх.** `grep -n` виводить **повний рядок** — тобто сам секрет
> опиняється в stdout, а звідти в контексті агента й у логах. Перевірка
> безпеки не має ставати каналом витоку.

```bash
# -c: лише кількість збігів, без вмісту рядків
# ключі, паролі, контакти
grep -ciE 'key|token|secret|password|passwd|pat|api[_-]?key|@|\+380' ФАЙЛ

# connection strings усіх видів
grep -ciE 'postgres://|mysql://|mongodb(\+srv)?://|redis://|amqp://|mssql://' ФАЙЛ

# заголовки та впізнавані префікси ключів
grep -cE 'Authorization:|Bearer |-----BEGIN|AKIA|xox[bpasr]-|ghp_|github_pat_|sk-|glpat-' ФАЙЛ
```

Якщо лічильник ненульовий — **відкрийте файл в редакторі й подивіться очима**,
а не переганяйте вивід через термінал агента. Для швидкої перевірки «чисто чи
ні» достатньо `grep -q … && echo "Є ЗБІГИ"`.

### 3.2 Те, чого пошук НЕ знайде

Це найважливіший пункт чек-ліста. Grep ловить те, що має характерний префікс.
Найчастіше витікає те, що префікса не має:

- ПІБ і назви компаній у таблицях і вкладеннях;
- адреси з номером квартири чи офісу;
- суми, обсяги й дати, за якими клієнт відновлюється;
- **скріншоти** — на них PII видно найчастіше, а grep їх не бачить взагалі;
- назва самого файлу (`бриф-<назва-клієнта>-2026.md` розкриває клієнта ще до відкриття).

**Тому: пошук не замінює перегляд очима.** Після grep пройдіть документ
вручну зверху вниз.

### 3.3 Тест на реідентифікацію

Замінити ім'я — ще не анонімізувати. Спитайте: **чи вистачить решти, щоб
вгадати клієнта?** Комбінація «галузь + міста + обсяг + стек» на вузькому
ринку відновлює компанію за хвилини.

Що зазвичай треба узагальнити додатково: географію, назви конкретних систем,
рідкісні числові характеристики, згадки про нашу власну інфраструктуру.

### 3.4 Фінальний прохід

- [ ] Жодного справжнього ПІБ / email / телефону / адреси
- [ ] **Ідентифікатори теж під рішення.** Номер тікета, `txn`, ID замовлення,
      user ID — це псевдонімізовані персональні дані, а не «нешкідливі
      технічні поля»: у зв'язці з іншим джерелом вони відновлюють особу.
      Лишаєте — робіть це свідомо й запишіть чому, а не за замовчуванням
- [ ] Вигрузки замінені синтетичними рядками **того самого формату**
- [ ] Секрети — лише як імена env-змінних, без відтворення форми значення
- [ ] Скріншоти перевірені окремо або замінені текстовим описом
- [ ] Ім'я файлу не містить назви клієнта
- [ ] Пройдено тест на реідентифікацію (3.3)
- [ ] Обрано інструмент під **найвищу** категорію, що лишилась
- [ ] Задача після маскування все ще зрозуміла (тест із §2)

## 4. Категорія → інструмент

| Категорія | Що використовуємо | Чому саме це |
|---|---|---|
| 🟢 | Claude Code / Cursor на звичайній підписці | Чутливого вмісту немає; швидкість важливіша за все інше |
| 🟡 | План з договірною **no-train** політикою (Claude Team/Enterprise, Cursor Business з privacy mode). Якщо доступу немає — локальна модель через Ollama | Дані не мають потрапити в навчальну вибірку й не мають зберігатись довше за сесію |
| 🔴 | AI не використовуємо. Спершу санітизуємо до 🟡/🟢 — тоді працюємо з результатом санітизації | Ризик не покривається жодною політикою вендора: після відправки відкликати неможливо |

### Чому для 🟡 саме no-train, а не «просто акуратно»

🟡 — це маржа, собівартість години й наша внутрішня логіка. Витік тут не
створює інциденту безпеки, тому спокуса «та нічого страшного» найбільша — і
саме тому потрібне формальне правило, а не розсудливість у моменті.

Вирішальний критерій — **не шифрування, а договірна заборона на навчання**.
Безкоштовні й споживчі тарифи такої гарантії не дають; enterprise-плани дають
її письмово.

Але **«no-train» сам по собі нічого не доводить** про решту життєвого циклу
даних. Перед тим, як віднести інструмент до 🟡, перевірте окремо:

- **строк зберігання** — скільки діалог живе після завершення сесії;
- **логи** — чи потрапляє вміст у телеметрію й на який строк;
- **доступ підтримки** — чи може людина з боку вендора прочитати діалог;
- **видалення** — чи є механізм і чи поширюється він на бекапи;
- **регіон обробки** і наявність підписаного DPA.

Якщо вендор не підтвердив усі п'ять пунктів письмово — інструмент
залишається 🔴, а не 🟡, скільки б у нього не було «no-train» у маркетингу.

Локальна модель закриває всі п'ять питань одразу, але коштує якістю — тому
тримаємо її як запасний варіант для випадків, коли 🟡-даних у документі багато
і санітизувати їх дорого.

Окремо: **«enterprise-план» не робить документ безпечним сам по собі.** Він
переводить 🟡 у прийнятний ризик. 🔴 він не покриває — там працює лише
видалення значення з документа.

## 5. Окремо про креденшели інтеграцій

Те, що зараз лежить у n8n credentials, — найризикованіша категорія при
переході в код: у платформі воно сховане за UI, у репозиторії — ні.

- значення живуть у `.env` (у `.gitignore`) або в менеджері секретів;
- у коді, промптах і документах фігурує **лише ім'я змінної**;
- у документах для моделі — `<SECRET_OUT_OF_BAND>`;
- текстове правило підкріплюємо технічним: deny-правила на читання `.env`,
  `*.pem`, `*.key`, `id_rsa*` і `*credentials*` у `.claude/settings.json`.
  Шлях описуємо через `Read(...)`: Claude Code застосовує ці правила і до
  Bash-команд, що читають файл — **перевірено на `cat` і `head`**, дублювати
  їх як `Bash(cat:...)` для цих команд не потрібно;
- **але покриття тримається на розпізнаванні команди.** `base64`, `xxd`,
  `python3 -c`, читання з-під скрипта — **не перевірені**. Не вважайте
  `Read(...)`-глоб універсальною межею для шелу, поки самі не прогнали
  відповідний вектор. Деталі — `docs/injection-report.md`;
  Патерни за назвою пишемо **в усіх регістрах** (`*credentials*`,
  `*Credentials*`, `*CREDENTIALS*`): glob-матчинг чутливий до регістру;
- патерн за назвою має бути вузьким. `*key*` здається спокусливим, але
  блокує `node_modules/keyv/*` і будь-який `monkey.ts` — правило, що
  заважає щодня, вимкнуть через тиждень;
- **і перевіряємо, що воно працює.** У нас ці правила спершу не діяли
  взагалі — валідний JSON, який не захищав нічого. Деталі й причини —
  у `docs/injection-report.md`;
- ротація після кожного випадку, коли ключ міг потрапити в контекст.

## 6. Якщо секрет усе ж потрапив у модель

1. Вважати скомпрометованим — незалежно від політики вендора й від того, що
   «це був лише чат».
2. Ротувати ключ негайно. Спершу ротація, потім розбір.
3. Зафіксувати інцидент: що саме, куди, коли, хто, чи був діалог збережений.
4. Перевірити, чи не пішло воно ще й у git-історію:

   ```bash
   git log -S 'фрагмент-значення' --oneline --all
   ```

5. Якщо пішло в історію — ротація обов'язкова навіть після
   `git filter-repo`: форки й клони вже роздані.
