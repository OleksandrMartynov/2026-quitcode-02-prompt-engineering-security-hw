# Додати тести до модуля

## Роль

Senior TypeScript-розробник, який пише тести як **специфікацію очікуваної
поведінки**. Тест, що описує те, що код робить зараз, — це не тест, а знімок.

## Мета

Покрити вказаний модуль тестами, які виявляють розбіжність між тим, що модуль
**має** робити, і тим, що він робить.

## Контекст

- Модуль: `{{шлях до модуля}}` — перевірено на `app/src/quote.ts`.
- Наявні тести: `{{шлях до тестів}}` — перевірено на `app/src/quote.test.ts`
  (навмисно неповні, лише happy path).
- Раннер: `vitest`, запуск `cd app && npm test`. Типи: `cd app && npm run typecheck`.
- Проєкт ESM + `moduleResolution: NodeNext` — імпорти пишуться з розширенням
  `.js` (`from "./quote.js"`), навіть для `.ts`-файлів.
- Домен: грошові суми — **цілі числа в центах**. Операція ділення суми не має
  ні губити, ні створювати копійки.
- **Конвенція розподілу залишку:** зайві центи дістаються **першим** платежам.
  Інваріант суми від порядку не залежить, але точні масиви — залежать; без
  зафіксованої конвенції будь-яке падіння можна відхилити як «ти сам вигадав
  очікування». _(додано у v2 — див. «Результат прогону»)_

## Обмеження

- НЕ змінюй продакшн-код. Якщо тест падає — це знахідка, а не привід правити
  реалізацію під тест.
- НЕ послаблюй очікування, щоб отримати зелений прогін.
- Не додавай залежностей, не міняй конфіг раннера, не чіпай інші файли.
- Правити можна лише файл `*.test.ts` поруч із модулем.

## Acceptance criteria

- [ ] Для кожної експортованої функції виписано щонайменше один **інваріант** —
      твердження, яке має триматись для будь-якого валідного входу — і на нього
      є окремий тест. Для функції, що ділить суму на частини, інваріант описує
      зв'язок між входом і **сумою всіх елементів результату**.
- [ ] Є щонайменше 3 тести з входами, де сума **не ділиться націло** на
      кількість частин (різні залишки), і кожен перевіряє результат **цілком**,
      а не лише його довжину чи тип.
- [ ] Покрито межі: `0`, від'ємні значення, відсоток поза діапазоном `0..100`,
      дробові години, кількість частин `1`.
- [ ] **Жодне очікування не підігнане під фактичний вивід коду.** Якщо
      інваріант не збігається з результатом — тест лишається червоним.
- [ ] Кожен тест названий поведінкою («ділить суму із залишком без втрати
      центів»), а не назвою функції («splitInstallments works»).
- [ ] Залишки в тестах **різні** (1, 2, 3, 4 центи), а не той самий випадок
      під різними числами.
- [ ] Усі наявні тести збережені дослівно: жоден не видалений і не послаблений.
- [ ] `cd app && npm run typecheck` без помилок.
- [ ] Наведено фактичний вивід `cd app && npm test`: скільки passed / failed,
      назви червоних тестів і кількість тестів до і після (`було N → стало M`).
- [ ] Для кожного червоного тесту вказано клас: **(A) дефект коду** або
      **(B) невизначена специфікація — потрібне рішення людини**.

## Формат відповіді

1. Файл тестів цілком.
2. Вивід `npm test` як є.
3. Таблиця падінь: `тест | вхід | очікували | отримали | ймовірна причина (файл:рядок)`.
4. Класифікація падінь на (A) дефект коду і (B) невизначена специфікація.

## Stop

Зупинись, коли тести написані й запущені. Якщо вони червоні — **не чіпай
продакшн-код**, щоб їх позеленити, і не послаблюй очікування: покажи таблицю
падінь і чекай на рішення людини. Не пропонуй рефакторинг і не додавай тестів
на функції, яких у модулі немає.

## Результат прогону — 2026-09-12

- **Запуск:** `prompts/add-tests.md` → `app/src/quote.ts`, vitest 5, Node 24.
  Перед виконанням — крок meta-prompting («що б ти тут покращив»).
- **Вийшло:** `4 → 31` тест, `11 failed | 20 passed`. Усі 4 наявні тести
  збережені дослівно й лишились зеленими.
- **Знайдена вада:** `splitInstallments()` у `app/src/quote.ts` —
  на момент прогону `Math.round(total/parts)`
  рахується один раз і копіюється на всі платежі. Дефект **двосторонній**:
  `(100,3)` → `[33,33,33]` = 99 (цент зник), `(100,6)` → `[17×6]` = 102 (два
  центи вигадано), `(5,2)` → `[3,3]` = 6, бо `Math.round(2.5) = 3` двічі.
  Те саме на від'ємних сумах — поверненнях коштів.
- **Stop-правило витримало:** `quote.ts` не змінений (sha256 `9e95cc0ab2d5057a`
  до і після), очікування не послаблені.
- **Що довелось поправити в промпті (v1 → v2):**
  1. Не була задана **конвенція розподілу залишку**. AC вимагав перевіряти
     масив цілком, але не казав, кому дістається зайвий цент — тобто автор
     тесту мусив вигадати конвенцію, і будь-яке падіння можна було відхилити
     як «сам придумав очікування». Додав у «Контекст».
  2. AC вимагав покрити «відсоток поза 0..100», але не казав, що має статися:
     кинути, клампити чи повернути 0. Через це 3 падіння `estimateTotalCents`
     — не дефект коду, а **невизначена специфікація**. Додав обов'язкову
     класифікацію падінь на (A) і (B): без неї людина не бачить, де рішення
     очевидне, а де потрібна її домовленість.
  3. `typecheck` згадувався в «Контексті», але його не було в AC — формально
     можна було здати файл, що не компілюється під `strict`.
  4. Не було заборони видаляти наявні тести: промпт дозволяв правити
     `*.test.ts`, тобто тихо прибрати незручний happy-path тест.
- **Урок про сам промпт.** AC «є тест на інваріант» виявився слабшим за AC
  «жодне очікування не підігнане під фактичний вивід». Перший дає тест, який
  можна написати так, щоб він пройшов. Саме другий тримає набір червоним і
  перетворює прогін на знахідку.
